# M3.5 friction notes

What surfaced while building the server-side aggregate stream — the wire format the dashboard actually wants, per [`WIRE.md`](../WIRE.md). M3.5 sits between M3 (throughput characterisation) and M4 (failure modes), and is the prerequisite for M4: the failure-mode tests are only meaningful at firehose rates, and at firehose rates the raw-event wire `/live` doesn't survive the round trip to the dashboard. M3.5 introduces `/live-agg` carrying per-host tick aggregates instead of every raw event.

This note tracks the friction from step 1 (the smallest end-to-end slice — `cpu_avg`/`cpu_sd`/`cpu_n` on a 200ms tick clock). Subsequent steps add anomaly counts, requests stats, globals, and snapshot history per `WIRE.md`; their friction will be appended.

## What we wished pond exposed natively

### Tick-driven aggregate over a partitioned series — RESOLVED in pond 0.13.0

**Status: closed. Pond 0.12.0 shipped `Trigger.clock(seq)` + the synchronised partitioned-rolling overload; pond 0.13.0 added the `AggregateOutputMap` overload on `LivePartitionedSeries.rolling` that closes the multi-stat-per-column gap.**

Step 1's aggregate-stream work now collapses to:

```ts
import { Trigger, Sequence } from 'pond-ts';

live.partitionBy('host').rolling(
  '1m',
  {
    cpu_avg: { from: 'cpu', using: 'avg' },
    cpu_sd:  { from: 'cpu', using: 'stdev' },
    cpu_n:   { from: 'cpu', using: 'count' },
  },
  { trigger: Trigger.clock(Sequence.every('200ms')) },
);
```

One pipeline, one per-host 1m buffer, three named outputs. `cpu_n` carries the bucket's own count — gating signal for the consumer ("are mean/sd backed by enough samples to be meaningful?"). The trigger only controls *when the bucket reports*; the bucket is the bucket.

What the experiment got right after multiple iterations + library-side feedback:

- **`Trigger.clock(Sequence.every('200ms'))`** — synchronised tick clock with the same `ts` for every host's row at boundary T. Pond's `setInterval` equivalent (`HostAggregator.tick(now)`) is gone.
- **`AggregateOutputMap`-shaped mapping** — three named outputs from one source column, sharing one rolling buffer (vs three pipelines × three buffers in the v0.12.0 trial).
- **Auto-injected partition tag** — `e.get('host')` works on the unified output even though `host` isn't in the mapping. Listing it would still hit `LivePartitionedSyncRolling`'s collision check, which is fine because the auto-injection is the actual contract. The library agent's docstring now matches.
- **Bucket-count `cpu_n`, not per-tick** — the conceptual correction the library agent made during 0.13.0 review: the count is a property of the bucket itself, useful for gating directly (`cpu_n >= 30`). Per-tick semantics matter only for rate / anomaly density, which are by definition a separate (shorter) window — to be added in step 4+ as a parallel rolling carrying `n_current` plus the anomaly-density columns.

What's left as residual experiment-side work:

- The per-`ts` row collation across partitions — `pond` emits one event per partition per boundary, the experiment groups them into a single `aggregate-append` wire frame per `ts` via a microtask-deferred drain. Could be a library helper (`view.batchByEventKey()`?) but is small enough that user code is fine.
- Wire envelope encoding (`AggregateAppendMsg` → JSON). Not pond's domain.

### Storage and throughput trade-off (mostly closed in pond 0.14.0)

The first profile-driven asks the experiment surfaced (PR #14's `profile-analysis.md`) both landed in pond 0.14.0:

- **`estimateEventBytes` removed** — the 6.2% per-push self-time line at the M3 ceiling. `retention.maxBytes` (the only consumer) was a speculative pre-1.0 feature and got dropped at the same time.
- **Trusted-pipeline routing on `LivePartitionedSeries.#routeEvent` / `collect()` / `apply()`** — the `Event → row → Event` round-trip at every routing hop is gone, replaced by an internal `_pushTrustedEvents` fast path that skips `#validateRow` + `Event` reconstruction when the source-and-target schemas are guaranteed identical (which they always are at internal hops). Closes the ~7% combined `#validateRow` + `Event` constructor self-time the V3 profile flagged.

Measured impact on `bench:agg` at the same load points:

| Config           | v1 heap (manual) | v3 (pond 0.13)  | v4 (pond 0.14)  |
| ---------------- | ---------------- | --------------- | --------------- |
| 9k/s             | 108 MB           | 187 MB (1.7×)   | **141 MB (1.3×)** |
| 87k/s            | 868 MB           | 1,701 MB (2.0×) | **1,418 MB (1.6×)** |
| 92k/s × 1k hosts | 865 MB           | 2,360 MB (2.7×) | **1,181 MB (1.4×)** |
| Ceiling rate     | 410k/s           | 208k/s (51%)    | **256k/s (62%)** |
| Ceiling tick fps | 4.73             | 1.33            | **1.73**        |

V4 closes most of the moderate-load heap regression (1.4–1.6× vs V1, was 2.0–2.7× in V3) and recovers ~23% of V3's ceiling throughput. The trusted-pipeline change is the bigger win on heap (no per-routing-hop `Event` allocation); the byte-estimate removal is the bigger win on throughput.

Residual gap to V1 at the ceiling regime is now ~38% (was 51% in V3). Remaining contributors per the V4 profile:

- **`LivePartitionedSyncRolling.ingest`** — 8.2% self time. The rolling-stats incremental update per event. Pond's reducers do a per-event running computation (Welford's stdev, etc.); HostAggregator deferred all stats work to the 200ms tick. Reducer batching (associative Welford over a run of events) would close this; not blocking step 1's correctness.
- **Per-event GC pressure** — 35.6% in V4 vs 28.7% in V1. Mostly from `Event`/`Time` allocations on emit, plus the per-event reducer-state updates. Reducer batching would also help here.

For step 1's expected dashboard rates (≤100k/s) pond's V4 is comfortable: sub-2ms p99 latency, ≤6% minor GC, no missed ticks. The remaining ceiling gap is informational input for any future incremental-reducer batching pass.

### Anomaly-density requires a "give me all bucket samples" reducer — RESOLVED in pond 0.14.2; perf-recovered via fused rolling in 0.15.0

**Status: closed.** Pond 0.14.2 shipped the built-in `'samples'` reducer (V7); pond 0.15.0 shipped the keyed-form fused multi-window rolling RFC'd in PR #20 (V8). The V6 → V7 → V8 progression collapses, in two library releases, from a hand-rolled deque to a single one-line pond call.

Step 4's anomaly-density columns (`anomalies_above[i]` / `anomalies_below[i]`) need, per tick per host, the count of samples in the leading-edge slice that exceed `cpu_avg ± thresholds[i] * cpu_sd`. The natural pipeline shape is two synchronised rollings:

```ts
const baseline = live.partitionBy('host').rolling('1m', {
  cpu_avg: { from: 'cpu', using: 'avg' },
  cpu_sd:  { from: 'cpu', using: 'stdev' },
  cpu_n:   { from: 'cpu', using: 'count' },
}, { trigger });

// What we want — but doesn't work yet:
const current = live.partitionBy('host').rolling('200ms', {
  // CustomAggregateReducer that returns the bucket's full value list
  cpu_samples: { from: 'cpu', using: (vs) => vs.slice(), kind: 'array' },
}, { trigger });
```

Two blockers in pond 0.14:

1. **Custom function reducers are rejected at runtime on `LivePartitionedSeries.rolling`** with the explicit error `"custom function reducers are not supported on live rolling. Use AggregateOutputMap aliases (...) to compose multiple built-in reducers from one source column."` Snapshot-side `TimeSeries.rolling` accepts custom reducers; the live-side parity gap is the active restriction.

2. **No built-in returns the bucket's full sample list.** `'keep'` returns the constant value when all bucket entries agree, else `undefined` — surprising naming. `'unique'` dedups (loses cardinality, defeats counting). `'top${N}'` is bounded (drops samples past N). `'avg'`/`'stdev'`/`'sum'`/etc. reduce to scalars.

**Library timeline:**

- `samples()` queued 2026-05-02; shipped in pond 0.14.2 on 2026-05-03.
- V7 perf diff (PR #19) characterised the cost of running two parallel rollings clocked off one trigger: ~19% throughput regression at ceiling, ~17% heap bump at 87k/s. The cost was in pond's per-event hot paths doubling (`#routeEvent` 15.0% → 28.9% inclusive, `LivePartitionedSyncRolling.ingest` 11.5% → 25.0%) — not in the `samples` reducer itself.
- That data motivated the fused multi-window rolling RFC (PR #20), which proposed a keyed-form API: `rolling({ '1m': {...}, '200ms': {...} }, { trigger })`. **Shipped in pond 0.15.0 on 2026-05-05.** V8 migration of `aggregate.ts` (this commit / follow-up PR) collapses the two `byHost.rolling(...)` calls to one fused call.

A `tap()` primitive (general "see every bucket value as it goes by") remains on the backlog — the user-facing flavor settled on a per-event observer callback `(event, host) => void`; orthogonal to fused rolling.

V6 → V8 progression on `aggregate.ts`:

| Stage | Shape                                                                                              |
| ----- | -------------------------------------------------------------------------------------------------- |
| V6    | One pond rolling (1m baseline) + manual per-host `{ts, value}[]` deque off `live.on('batch', cb)`. |
| V7    | Two pond rollings (1m baseline + 200ms slice) on shared trigger; per-`(ts, host)` parts buffer joins them. |
| V8    | One fused pond rolling with both windows. One ingest pass, one event per partition per tick.       |

```ts
// V8 — pond 0.15.0
const fused = byHost.rolling(
  {
    '1m': {
      cpu_avg: { from: 'cpu', using: 'avg' },
      cpu_sd:  { from: 'cpu', using: 'stdev' },
      cpu_n:   { from: 'cpu', using: 'count' },
    },
    '200ms': {
      cpu_samples: { from: 'cpu', using: 'samples' },
    },
  },
  { trigger },
);
fused.on('event', e => { /* both windows' columns on one event */ });
```

The per-`(ts, host)` parts buffer / `partsFor` / two-listener reconciliation — gone. The collation that remains is just per-tick frame coalescing (collect N hosts at the same `ts` into one wire frame).

Cite: [`packages/aggregator/src/aggregate.ts`](../packages/aggregator/src/aggregate.ts), [`friction-notes/rfcs/fused-rolling.md`](rfcs/fused-rolling.md), [`packages/aggregator/scripts/profile-analysis-v6-vs-v7.md`](../packages/aggregator/scripts/profile-analysis-v6-vs-v7.md).

### Non-partitioned rolling bottlenecks at firehose rates — RESOLVED in pond 0.15.2

**Status: closed. pond-ts 0.15.2 shipped an O(1)-amortised eviction path on every live rolling class, citing this PR's friction note in the changelog. Step 6 now uses the natural-API shape — `live.rolling({'1s': {events_per_sec: 'count'}}, {trigger})` — without the perf cliff.**

Step 6 ships per-tick globals on `/live-agg` (`events_ingested_total`, `events_per_sec`, `evicted_total`) so the dashboard's headline numbers reflect the producer's actual gRPC throughput rather than the dashboard's down-scaled view. The natural pond shape is the unpartitioned sibling of the partitioned fused-rolling we ship for the per-host work:

```ts
const globalsStream = live.rolling(
  { '1s': { events_per_sec: { from: 'cpu', using: 'count' } } },
  { trigger },
);
globalsStream.on('event', (e) => {
  const eps = e.get('events_per_sec');
  if (typeof eps === 'number') latestEventsPerSec = eps;
});
```

The first commit on this branch tried exactly this on pond 0.15.1. Tests passed. **Throughput collapsed from ~88k/s to ~21k/s at the 87k/s bench point** — a 4× regression worse than the V7→V6 gap PR #19 documented. The aggregator dropped from 5 fps to 1.2 fps tick emission, p99 inter-arrival climbed from ~200 ms to ~1 s, the system was choking.

Root cause: `Array.shift()` in the rolling's eviction path is O(N) where N is the live deque size. At firehose rates the deque has 1k–100k+ live entries; per-ingest eviction means O(N) work *every event*. The partitioned variant shards across N hosts so each partition's deque is small (~rate/N) and the cost is hidden; the non-partitioned variant takes the full firehose into one deque and exposes the cliff. Same code path, drastically different deque sizes.

pond-ts 0.15.2 fixed the eviction loop in `LiveFusedRolling`, `LivePartitionedFusedRolling`, `LiveRollingAggregation`, and `LivePartitionedSyncRolling` — replacing `entries.shift()` with a head-index pointer + amortised batched compaction (proportional guard: splice off the dead prefix when it grows past half the array). Per-event cost is now O(1) amortised at every live-window size. Library's own regression bench shows a 21× speedup on the worst-case shift pattern (50s window, 50k fill + 50k evict).

Step 6 now ships the natural shape. Verified: throughput at the 87k/s bench point recovers to step-5 parity; no measurable per-event overhead at the 9k/s and 92k×1k bench points either. The cumulative counters (`events_ingested_total`, `evicted_total`) and the `firstEventTs` for `window_age_seconds` still come from manual `live.on('batch'/'evict')` callbacks — pond doesn't have a "running cumulative counter" reducer, and even if it did, those callbacks are already part of the API.

**Library timeline:**
- 2026-05-06 morning: PR #26 lands the manual-counter workaround + friction note documenting the cliff.
- 2026-05-06 morning (same day): pond-ts 0.15.2 ships, citing PR #26 in the changelog. Eviction loop fixed across all four live-rolling classes.
- 2026-05-06 morning: PR #26 follow-up commit re-enables the natural-API shape and updates this note.

Round-trips between the experiment and the library on the M3.5 anomaly-density slice:

| `samples()` reducer needed | 0.14.2 | overnight  |

### Snapshot history for the aggregate stream

`WIRE.md`'s snapshot envelope expects the most recent N ticks across all hosts so a connecting client can paint the chart's existing history immediately. Step 1 ships an empty snapshot — the dashboard fills in as ticks arrive — because the right shape on the server is unclear:

- A bounded ring of past `HostTick[]` frames is straightforward but lives outside pond, and re-implements what `LiveSeries.toJSON()` does for raw events.
- The natural pond API would be: the same tick aggregator above also exposes `lastN(durationMs)` returning the recent backfill in one call. Then snapshot-on-connect is `JSON.stringify({ thresholds, rows: ticks.lastN('5m') })`.

Without that, a custom implementation has to choose a memory budget, a flush cadence, and a per-tick row format that's separately stored from pond's `LiveSeries`. Three orthogonal decisions, each easy to get wrong.

Deferred to a step-2 PR; flagging here because it's the API gap the deferral makes visible.

### Wire-format envelope versioning

`@pond-experiment/shared/wire.ts` now has four message types: `snapshot`, `append`, `aggregate-snapshot`, `aggregate-append`. The two pairs are structurally identical except for `rows`. As the dashboard migrates `/live` → `/live-agg` and the eventual full `WIRE.md` shape lands (anomalies, globals, requests), the message-type sprawl gets worse.

A library-shipped envelope — `WireMsg<TRow>` parameterised by the row schema, with `type: 'snapshot' | 'append'` not "duplicated per stream" — would let `@pond-experiment/shared` define one `RawWire = WireMsg<WireRow>` and one `AggregateWire = WireMsg<HostTick>` instead of four bespoke type aliases. Opt-in for library users; standardises the snapshot+append protocol across products.

Falls in the `useRemoteLiveSeries` RFC's lap — that hook is where the envelope is parsed on the client, so envelope ergonomics are its problem.

Cite: [`packages/shared/src/wire.ts`](../packages/shared/src/wire.ts).

### "Latest value per partition" client-side primitive

Step 2's `AggregateProbe` needs the most recent `HostTick` per host. There's no pond/`@pond-ts/react` primitive for this on a stream of partitioned events — `useCurrent(live, { col: 'avg' }, { tail: '1m' })` does whole-series rollups but not per-partition latests. Step 2 rolls this by hand in `useRemoteAggregateSeries` (a `Map<host, HostTick>` updated on each frame).

A hook like `useLatestPerPartition(live, 'host')` returning `ReadonlyMap<host, EventForSchema<S>>` would close the gap. It's the per-partition equivalent of "the chart shows the most recent state, not a rollup over a window" — a common operational view that's trivially mis-implemented (e.g., race conditions on closures, stale-state in WS handlers; both of which bit step 2's first implementation before the `latestRef` fix).

Sits in the `useRemoteLiveSeries` / `@pond-ts/react` RFC's footprint.

Cite: [`packages/web/src/useRemoteAggregateSeries.ts`](../packages/web/src/useRemoteAggregateSeries.ts).

### Aggregate-side schema-as-protocol parity

Step 3 will mount a client `LiveSeries<aggregateSchema>` to drive the bands UI off the aggregate stream. Doing so needs an aggregate `SeriesSchema` declaration that mirrors the wire `HostTick` shape — same friction the raw-event side surfaced in M1, now on the aggregate side. A library codegen / synchronisation primitive that pairs a wire row type with a `SeriesSchema` (so adding a column to one breaks the other) would catch a class of bugs the experiment will keep producing per wire-shape change.

Deferred to step 3's friction increment when the schema actually exists.

### Per-partition `aggregate` must re-declare the partition column — RESOLVED in pond 0.16.1

The dashboard's chart-decimation work (this note's sibling under "Friction not directly on pond") moves the per-host CPU downsample off a hand-rolled JS bucketer onto pond's native `aggregate`. The natural shape is exactly what the API documentation promises:

```ts
aggSnapshot
  .filter(...)
  .partitionBy('host')
  .aggregate(Sequence.every('600ms'), {
    cpu_avg: 'avg',
    cpu_min: 'min',
    cpu_max: 'max',
    cpu_n: 'last',
  })
  .toMap((g) => g.toPoints());
```

Pre-fix this threw `PartitionedTimeSeries: column "host" not in schema` at the rewrap step — the aggregate succeeded inside each partition, but `PartitionedTimeSeries.aggregate(...)` couldn't re-establish a partitioned wrapper over a result whose schema no longer carried the partition column (because the user's reducer map didn't include it).

Workaround during the experiment was mechanical — add `host: 'first'` to every partitioned-aggregate reducer map.

**Library timeline:** PR #29 lands the workaround + this friction note on 2026-05-06 morning. Pond 0.16.1 ships the same day with auto-injection of the partition column at `PartitionedTimeSeries.aggregate(...)` and `.rolling(...)` — `'first'` is by-construction-correct since every row in a partition shares that column's value. User-supplied mappings for the partition column win (auto-inject is a no-op when the user has already opted in). Composite partitions (`partitionBy(['host', 'region'])`) auto-inject every partition column.

After bumping to 0.16.1 the workaround can drop entirely:

```ts
.aggregate(Sequence.every('600ms'), {
  cpu_avg: 'avg', cpu_min: 'min', cpu_max: 'max', cpu_n: 'last',
})
```

Cite: pond-ts CHANGELOG.md entry for 0.16.1 (PR #128); [`packages/web/src/useDashboardData.ts`](../packages/web/src/useDashboardData.ts) — workaround dropped after the bump.

### Bounded-memory rolling via sampling — `live.partitionBy(...).sample({ stride: N })` — RESOLVED in pond 0.17.0

**Status: closed.** Pond 0.17.0 shipped the operator the RFC asked for, with the API shape the RFC specified — `series.sample({ stride | reservoir })` on snapshot side, `live.sample({ stride })` on the live side, both chainable after `partitionBy(...)` so per-stream thinning is the natural default. The 0.17.0 changelog entry [cites the experiment's RFC by URL](https://github.com/pjm17971/pond-ts/pull/129) — full RFC → library work → integration loop closed in two library releases.

**Integration on the experiment side:** the hand-rolled per-host stride sampler at the gRPC ingest hop (PR #33's prototype — `Map<string, number>` counters + a `pass = c % stride === 0` filter before `live.pushMany`) has been removed. The aggregate pipeline now reads:

```ts
const fused = live
  .partitionBy('host')
  .sample({ stride: SAMPLE_STRIDE })   // ← pond 0.17.0
  .rolling({ '1m': mapping, [`${tickMs}ms`]: slice }, { trigger });
```

…with `SAMPLE_STRIDE` plumbed through `AggregateOptions` instead of `IngestOptions`. The rolling sees ~1/N events per host as before; the difference is what's **upstream** of the sample.

**Wire-correctness fix that fell out:** `live.on('batch', cb)` (the cumulative-counter listener) and the non-partitioned globals rolling for `events_per_sec` both sit upstream of any `.sample(...)` op — pond's contract per the 0.17.0 changelog:

> `live.stats().ingested` and `live.on('batch', cb)` are upstream of any `.sample(...)` op — they continue counting true throughput; only consumers downstream see the thinned stream.

So `events_ingested_total`, `events_per_sec`, and `requests_ingested_total` now reflect the **true gRPC firehose** under any stride. Pre-0.17 the prototype's stride sampler dropped events at the gRPC ingest hop, undercounting these by the stride factor — the RFC's "counts post-sample" caveat. The dashboard's headline numbers are now correct end-to-end. (Test in `aggregate.test.ts` pins this: at stride 4, `cpu_n` reads ~N/4 while `events_ingested_total` reads N exactly.)

**RFC's reasoning held:**

- The chained-after-`partitionBy` placement avoids the bias trap by construction. The RFC's worked example was the experiment's own producer (fixed-order host emission + naive global counter → drop 72 of 80 hosts deterministically); the library docs the same pattern with the same recommendation.
- Single-pass thinning: pond's stride op keeps a closure-captured counter inside a `LiveView<S>`, so the chainable surface (`filter`, `rolling`, `reduce`, etc.) is immediately available downstream. Same shape the RFC asked for.
- The reservoir variant (`{ reservoir: { size: K } }`) shipped on the snapshot side (`TimeSeries`/`PartitionedTimeSeries`); the live-side reservoir is queued for v0.18.0+ behind Phase 4.5 milestone A's `LiveChange` channel — Algorithm R's random-slot replacement produces non-prefix evictions which the existing `'evict'` event protocol can't model. (RFC's `'evict' | 'replace'` proposal landed in the deferred section pretty much verbatim.)

What's next on the experiment side, deferred to follow-up PRs:

- **Retention tuning.** Now that the rolling state is bounded by stride, the LiveSeries deque (currently `maxAge: '30s'`) is the dominant memory consumer at firehose. Pre-0.17, ingest sampling kept the deque small as a side-effect; post-0.17 the deque sees the full firehose. The V9 bench below already isolates this — the 92k/s × 1k-hosts row's heap regression vs v4 lives in the LiveSeries deque, not the rolling. Shrinking retention to `'1s'` should recover most of it without functional loss (the rolling owns its own state; retention is just a snapshot-on-connect buffer for `/live`).
- **Long-baseline opportunity.** With per-host stride 10, a 5-minute baseline fits the same heap budget as the current 1-minute. Worth swapping `'1m' → '5m'` once retention tuning lands — the dashboard's `cpu_sd` becomes a much better "is this host in a different regime than usual?" signal at the longer window. Wire shape unchanged; just longer baseline.

## Friction not directly on pond

### Recharts as the dashboard's render bottleneck — case for `@pond-ts/charts`

Step 7's min/max envelope, step 8's snapshot-history backfill, and the firehose-rate throughput sweep that shipped alongside step 8 surfaced a cumulative dashboard-side perf cliff. After the wire-and-pipeline side was already lean — per-tick aggregate stream replacing the raw firehose, 30s retention bounding the aggregator heap, filter-before-partition + per-host pond-native `aggregate` downsample bounding the cpu memo at 3-5ms steady — the browser was rendering at ~1 fps with 10 hosts visible at 70k events/s. Two tabs open → "Aw, Snap!" Chrome OOM. `?perf=1` instrumentation in the cpu memo isolates the cause: the memo finishes its work in 7-37 ms, then 1-5 seconds of wall-clock pass before the next sample fires. Recharts' SVG render dominates the frame budget by an order of magnitude.

Worst-case SVG node count per render at 10 enabled hosts, 5min × 5fps/host = 1500 ticks/series, three series per host (smoothed line + ±σ band + min/max envelope when toggled):

- 10 lines × 1500 points × (1 line + 1 scatter) ≈ 30k nodes
- 10 ±σ bands × 1500 polygon points ≈ 15k nodes
- 10 min envelopes + 10 max envelopes × 1500 points ≈ 30k nodes
- per-tick anomaly dots, ~1500–1700 at firehose ≈ 1.5–2k nodes

≈ 75–80k SVG elements, each diffed and re-rendered per 200 ms throttle tick.

**Quick-win that shipped:** decimate per-series to a target point count (currently `TARGET_CHART_POINTS = 500`, tuned to the chart's ~420px width). Done as a per-partition `aggregate(Sequence.every(bucketMs), { cpu_avg: 'avg', cpu_min: 'min', cpu_max: 'max', ... })` so spike preservation falls out of pond's built-in `'min'` / `'max'` reducers — a bucket containing a single-tick spike still reports the spike in the `min`/`max` envelopes. Cuts the SVG node count ~3×, restores fluid rendering at moderate rates (14 fps with 1 host, 4 fps with 5 hosts at 50 events/s).

The decimation does not save the firehose case at 10 hosts. After 3× downsample the chart still renders ~25–30k SVG elements; SVG simply can't keep up with React's reconciliation pace at that count, regardless of how clean the source data is. The frame rate stays around 1 fps. That's the canvas-vs-SVG cliff, not a data-volume problem.

**Right answer: `@pond-ts/charts`** — a small canvas-based chart primitive that the visualization milestone (M5 extraction sweep) carves out as a sibling package to `pond-ts` / `@pond-ts/react`. Charts already require domain knowledge of pond's `Sequence`, `partitionBy`, and event-vs-row shapes (the chart input is the same `{ts, ...cols}[]` `toPoints()` produces); a canvas implementation specialised for that input gets to skip Recharts' generic-data-table abstraction and the per-frame React reconciliation Recharts induces. Other dashboards inside the team will hit the same SVG cliff at any non-trivial fan-out, so pulling it out of the experiment as its own package pays back immediately.

Constraints worth carrying into that package's design:

- Streaming-first: accept `LiveSeries` / `useWindow` / `aggregate` outputs, not just static arrays. The chart decides its own decimation grid (or accepts a `Sequence` from the caller).
- Spike-preserving decimation must be the default for envelope / min / max signals — pond's reducers already encode the right per-signal semantic, the chart just has to plumb the picker through.
- Anomaly / sparse markers stay full-resolution alongside decimated continuous signals. They're a separate channel, not a downsample target.
- Render at the throttle cadence even with 30+ visible series; this experiment's CPU section is the canonical stress test.

Cite: [`packages/web/src/useDashboardData.ts`](../packages/web/src/useDashboardData.ts) — `TARGET_CHART_POINTS`, the `?perf=1` instrumentation in the cpu memo, and the `aggregate(Sequence.every(...), { ... })` per-partition downsample. [`packages/web/src/Chart.tsx`](../packages/web/src/Chart.tsx) — the Recharts `<ComposedChart>` whose SVG node count caps the experiment's render budget.

### Multiple listeners on `live.on('batch', …)`

The fanout layer (`fanout.ts`) and the aggregate layer (`aggregate.ts`) both subscribe to `live.on('batch', …)`. Pond supports multiple listeners (verified end-to-end in tests), but the implicit fan-out of one batch to N consumers is doing the same per-event work N times — every event is visited by every listener for `e.get('host')`, `e.key().timestampMs()`, etc.

The cost hasn't been measured for step 1 (only one listener at a time on the existing throughput rig — fanout in M3, aggregate in M3.5 step 1 with no concurrent fanout in bench). Worth re-running the saturation sweep with both listeners attached once the dashboard cuts over to `/live-agg` and `/live` is retired — even better, keep `/live` retired and the comparison falls out of the bench.

A library API to "subscribe to per-host partition only" rather than "subscribe to all events and partition in user code" would let consumers express their interest more cheaply. Likely related to the `partitionBy` work above — a `live.partitionBy('host').on(host, batch)` would naturally restrict the visited set per listener.

### Per-subscriber wire projection

The aggregator broadcasts the same `aggregate-append` frame to every connected `/live-agg` client. At firehose × 10 hosts the chart can only legibly render the busiest 5 — so the dashboard initially clipped client-side (`hosts.sort(...).slice(0, 5)` inside the CPU memo), shipping ~10 host-rows per frame to use ~5 of them. That's a wire-cost / chart-legibility mismatch every fan-out streaming server eventually wants to fix the same way: **let each subscriber tell the server what slice of the stream it wants, and project per-client at broadcast time**.

This experiment's PR #34 makes that move:

- `/live-agg` clients send `{type:'set-top-n', n: 5}` over the WS after open.
- Server keeps a `Map<WebSocket, ClientPrefs>` and at each 200 ms tick projects the broadcast frame to each client's view (sort rows by `cpu_avg` desc, take top-N).
- `useRemoteAggregateSeries(url, topN)` exposes the prop; reconnect re-arms the preference; prop updates send a fresh control message without bouncing the socket.

The pattern is general — top-N is the example, but any subscriber-specific filter / projection (region, severity threshold, host allowlist, sampling rate) wants the same scaffolding. The friction observation:

**Pond's `live.on('batch', cb)` ships the same payload to every listener.** That's the right primitive — pond doesn't know about subscribers — but every fan-out server ends up reinventing the same shape on top of it: a per-subscriber-prefs map + a projection callback at broadcast time + a control channel for prefs updates + (optional but real) hysteresis to stabilise the cut as inputs jitter. The aggregator's broadcast loop is now ~30 lines doing exactly that; doubling it to a second projection (e.g. region filter) would re-write the same code with a different sort key.

A small library scaffold could absorb the recurring shape — something like:

```ts
const fanout = live.fanout<ClientPrefs>({
  defaultPrefs: { topN: null },
  project: (batch, prefs) => topN(batch, prefs.topN),
});
fanout.attach(socket, prefs);   // per-WS handle
fanout.update(socket, newPrefs); // control-channel update
fanout.detach(socket);
```

…where `live.fanout` returns a managed wrapper around `live.on('batch', ...)` that runs the project callback per attached subscriber and ships the result via `socket.send`. The library would own the per-subscriber map, the broadcast loop, and the `socket.readyState` gate; user code defines the prefs shape, the projection, and (optionally) a hysteresis function over consecutive frames.

This is a "the friction shows up the third time" call — first time was the original raw `/live` fanout (`fanout.ts`, no projection at all, single payload), second was M3.5's aggregate fanout (still single-projection, same payload to everyone), now top-N is the third. Worth flagging for the M5 RFC sweep before a fourth instance shows up. The next plausible one is per-client globals filtering (a host-allowlist subscriber wanting only their hosts' globals) — same shape again.

What pond gets right today and shouldn't lose:

- `live.on('batch', cb)` as the pure broadcast primitive — the projection layer should compose **on top of** it, not replace it. Subscribers that want the full stream (e.g. metric exporters, persistence sinks, dev tools) keep their straightforward access.
- Batch payload structure is already shape-stable across listeners; per-subscriber projection is a pure transform per call, no shared mutable state needed.

What's missing:

- **Per-subscriber state lifecycle.** Each WS attach/detach is paired with prefs creation/disposal; user code currently writes that bookkeeping by hand (`Map<WebSocket, ClientPrefs>` + `socket.on('close', ...)` + `socket.on('error', ...)`). A managed `attach` / `detach` is the cheap part of the scaffold but the most-copied part across implementations.
- **Hysteresis hook.** Top-N flicker at the boundary (host A drops to #6, then back to #5 a tick later, dragging the cut around) is the reason real production streams want hysteresis. The experiment shipped a rank-based version directly inside `projectAppend` (margin 1 — keep a host in the cut as long as its new rank is ≤ N + margin); see "Per-subscriber wire projection — hysteresis" below for the full algorithm. The library scaffold above would still benefit from a `hysteresis: (prevSelection, sortedRanking) => stableSelection` hook, because:
  - The dashboard's rank-based approach with a fixed margin works for the cpu_avg cut, but other projections (region allowlist, severity threshold) want different stability semantics — value-based deadband, time-based dwell, top-K-with-affinity. A hook lets the projection declare its own rule.
  - The experiment's hysteresis state lives on `ClientPrefs.lastTopHosts` and is hand-threaded through the broadcast loop (read-prefs → project → write-prefs-back). With a library scaffold, the framework would own the carry-over state; user code would just declare the rule.
  - Server-side hysteresis interacts with the slider UX: when `topN` changes, the carry-over set was sized for the old N and isn't valid for the new one. The experiment resets `lastTopHosts: null` on every `set-top-n`. A library scaffold could surface this as `onPrefsChange: (oldPrefs, newPrefs, hysteresisState) => hysteresisState`, defaulting to "reset on any prefs change" but giving the user a hook for migration.
- **Encode-once-per-projection-class.** When K subscribers share identical prefs (the common case for "everyone wants top-5"), the projection result is identical and could be encoded once and shared across their `socket.send` calls. The experiment doesn't bother (5 clients × 5 hosts × 200 ms is trivial), but at scale this is the same friction TimescaleDB / Kafka consumers solve via "compaction key" or "shared subscription" semantics.

Cite: [`packages/aggregator/src/server.ts`](../packages/aggregator/src/server.ts) — `ClientPrefs`, `projectAppend`, `parseControlMessage`, the `aggClients: Map<WebSocket, ClientPrefs>` and per-client encode loop. [`packages/web/src/useRemoteAggregateSeries.ts`](../packages/web/src/useRemoteAggregateSeries.ts) — `topN` prop, control-channel send-on-open + send-on-change, `wsRef` / `topNRef` to keep prop updates from churning the socket.

### Per-subscriber wire projection — hysteresis on the top-N cut

A direct extension of the per-subscriber wire projection above. **Problem:** strict top-N is a step function — at the rank boundary, two hosts with near-identical `cpu_avg` swap rank from one tick to the next, the cut flips between them at 5 fps, and the chart's per-host line + legend entry flashes in and out. Visible at the dashboard's typical fan-out (10 hosts) once two hosts are within ~1% of each other on `cpu_avg`. Annoying enough at fixed top-N; vivid the moment the user drags the slider into the boundary regime.

**Algorithm shipped (rank-based, margin M = 1):**

```
output = (strict top-N from sorted rows)
       ∪ (hosts in lastTopHosts whose new rank is in [N+1, N+M])
```

- **Strict top-N is unconditional**, so a new burst host vaulting from rank 20 to rank 1 is admitted on its first tick. Hysteresis only delays expulsion, never delays admission.
- **Carry-over:** a host that was in last frame's cut stays for one more tick if it's only one rank below the new cut. Visible cut size is `N` in stable state and `N+1` during single-rank boundary churn.
- **Sustained drop** (rank > N + M) expels the host even if it was in lastTopHosts. The cut isn't a one-way ratchet.
- **Cold start** (`lastTopHosts: null` — first frame after connect, or after a `set-top-n` change) collapses to strict top-N. The carry-over state warms up over the next frame.

**State lifecycle:**

- `ClientPrefs.lastTopHosts: ReadonlySet<string> | null` — written back into the prefs map by the broadcast loop after each `projectAppend` call. Mutating the live map entry rather than `Map.set(...)` because per-tick churn at C clients matters.
- Reset to `null` on `set-top-n`. The old carry-over set was sized for the previous `N` and would carry stale boundary entries through the new projection's first few frames.
- Reset implicitly on disconnect (the prefs entry is removed from `aggClients` on `socket.on('close', ...)`).

**Why rank-based (not value-based):**

Value-based hysteresis ("deadband on `cpu_avg`") needs a tuning parameter the user has to think about — what's a meaningful `Δcpu` margin? `0.01`? `0.05`? `1%` of the cut threshold? Rank-based is parameter-free with a sensible default; the only tunable is the margin in ranks, and `1` is the obvious starting point (the smallest non-zero value, which lets the chart smooth one tick of jitter without ballooning the visible cut).

If a workload genuinely needs value-based stability (e.g. small-N cuts where rank-1-margin still flickers because cpu_avg is genuinely noisy), the library-scaffold hook in the section above would let the projection declare its own rule.

**Why one-way (delay expulsion, not admission):**

A host that bursts decisively ought to appear immediately — that's the whole point of a top-N chart. Hysteresis on admission would make the chart sluggish in the regime that matters most (a host going hot). The cut's job is to react to incoming bursts; hysteresis is just to stop the regime where two near-equal hosts swap micro-second-to-microsecond at the boundary.

**The UX it enables:**

First iteration was a slider (1–15) + a chip row of all hosts ever in the cut, with "faded" styling for hosts not in the current frame's cut. Hysteresis made the slider feel sticky rather than jittery. Two UX problems surfaced once the slider was live:

1. **The chip row was lossy.** With server-side top-5, the chip row showed up to 10 chips (the union of hosts ever in the cut over the visible 5min window) with 5 solid + 5 faded. Faded vs solid is a subtle binary and hard to read at a glance. The user's eye couldn't quickly answer "which 5 are in the cut right now and how do they compare?"
2. **A continuous slider for a discrete value was wrong.** Top-N is integer-valued in a small range (1–15); a slider implies finer-grained control than the data supports. A discrete dropdown matches the type.

Second iteration replaced the chip row + slider with a **table** (`packages/web/src/sections/HostTable.tsx`):

```
Top [5 ▼] hosts by [1m CPU ▼]

┌────┬────────┬────────┬─────────┬───────┐
│ ✓  │ Host   │ 1m CPU │ Current │ Trend │
├────┼────────┼────────┼─────────┼───────┤
│ ✓  │ api-7  │ 73%    │ 65%     │ ▁▃▇▅  │
│ ✓  │ api-3  │ 66%    │ 59%     │ ▂▄▆▆  │
│ ...                                     │
└────┴────────┴────────┴─────────┴───────┘
```

Each row corresponds 1:1 to a host the wire is currently shipping. The "1m CPU" column shows the rank metric (or whatever the rank-by dropdown is set to); "Current" shows `current_avg` (200ms slice); "Trend" is a small canvas sparkline of the last ~12s of the rank metric. Server-side hysteresis still smooths the cut; the table just renders whatever's in the latest frame.

**Rank-by dropdown (wire extension).** The control message extends from `{type:'set-top-n', n}` to `{type:'set-top-n', n, by}` where `by` is one of `cpu_avg` / `cpu_sd` / `requests_avg` (the 1m baseline metrics — per-tick metrics like `current_avg` would make the cut thrash). Server's `parseControlMessage` validates against a known list (typo'd metric → hard reject), `projectAppend` reads `prefs.rankBy` for the sort key, hysteresis state is keyed on host so it carries cleanly across metric changes (though the experiment resets `lastTopHosts: null` on `set-top-n` for simplicity — the alternative would be carrying entries that are valid for the new metric's rank order, which is the next layer of nuance).

What this told us about the slider design pattern: **a single dropdown surface ("dropdown of dropdowns" — "Top N hosts by metric") is a far stronger UX primitive than a slider for top-N alone.** The slider's affordance was "more or fewer"; the table's affordance is "ranked by what, top how many" — two orthogonal questions, two dropdowns, immediately legible. The library-scaffold idea above could surface this as a UI hint (`{ kind: 'discrete-int', range: [1, 15] }` vs `{ kind: 'continuous', range: [0, 1] }`) so the dashboard side knows what shape of control to render.

**Cite:** [`packages/aggregator/src/server.ts`](../packages/aggregator/src/server.ts) — `TOP_N_HYSTERESIS_MARGIN`, `lastTopHosts` on `ClientPrefs`, `RANK_KEYS` runtime list, the `prefs.rankBy`-driven sort inside `projectAppend`, and `parseControlMessage`'s `by` field. Tests at `packages/aggregator/src/server.test.ts` cover the hysteresis cases (M=0 regression, stable-state convergence, single-rank boundary swap, sustained drop, burst entry, cold start) plus the rank-by cases (CPU vs req vs volatility producing different orders, null-on-rank-column sorts to bottom, hysteresis preserves across same metric). 2. **Ceiling rate held at ~210k/s — flat-to-slightly-worse than V4 (256k/s) and meaningfully below the V8 one-off claim (284k/s).** V5 looks more like V7 (209k/s, pre-fused) than V8 — suggesting V8's 284k may have been favorable conditions (cleaner system state, less GC noise) that don't reproduce on the current machine. 4. **92k × 1k hosts heap regression: 1,181 MB (V4) → 1,857 MB (V5).** Most plausibly attributable to per-partition fused-rolling state being 2× the storage of two separate rollings (V4's setup) at the 1000-partition cardinality. ### Phase B recommendation — Step 7 first

The V5 profile points at **Step 7 (LiveSeries numeric ring buffer) as the first Phase B PR**, with two reasons:

- **GC pressure (22.0%) is still the single largest cost line.** Even with lazy events helping, per-`pushMany` event allocations are dominant. The `ColumnarRingBuffer` (already shipped at step 1h) skips the `Event/Time` allocation path entirely — substrate-shape ingest. The structural fix.
- **The 78k/s latency regression (and 92k×1k heap blow-up) likely also stems from per-event allocation pressure.** Ring buffer should help both, and the same change that fixes the ceiling regression should fix the tail latency.
- **Step 3 Phase C (rolling fast path) is the secondary target at 12.9% self.** Half the magnitude of GC; should follow Step 7 once the substrate-shape ingest is in place (rolling state work then operates on a substrate-shape source naturally).

If Step 7 closes the 22.0% GC line to ≤10% AND brings ceiling back to V8's 284k+ territory, the strategic justification of the substrate is met on the streaming side. Step 3 Phase C then earns its slot from whatever the next bench surfaces.
