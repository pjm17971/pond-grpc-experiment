# M4 friction notes — late-data driver (milestone-B sequencing input)

What surfaced while executing pond-ts's [`grpc-late-data-validation.md`](https://github.com/pjm17971/pond-ts/blob/main/docs/briefs/grpc-late-data-validation.md) brief — the experiment-side work that drives milestone-B sequencing for the pond library. The brief asked four things:

1. **Phase 1** — generate controlled late data at the producer (env-configurable fraction / mean / tail / per-host bias, seeded RNG for reproducibility).
2. **Phase 2** — configure the aggregator's `LiveSeries` with `ordering: 'reorder'` + `graceWindow`.
3. **Phase 3** — instrument per-aggregation-stage correctness counters and a multi-replicate drift-comparison harness with run-to-run noise-floor estimation.
4. **Phase 4** (this note) — write the recommendation that drives milestone-B sequencing: does pond's current "rolling does not retroactively repair late events" behaviour matter at realistic experiment loads, or is the milestone better-described as a documentation gap?

The TL;DR of the recommendation is at the bottom; the body walks through the friction this exposed.

## Headline: `partitionBy` ordering is the real footgun

**The experiment shipped Phase 2 without observing this until Phase 3 ran end-to-end.** Setting `ordering: 'reorder'` + `graceWindow: 30000` on the source `LiveSeries` is **necessary but not sufficient** — `live.partitionBy('host')` defaults the per-partition sub-series to `ordering: 'strict'` regardless of the source.

Symptom: under `'reorder'` source + default partition, a late event the source accepts via `#insert`'s reorder branch is then routed to the partition's sub-series via `_pushTrustedEvents`. The sub-series's `#insert` sees the event as out-of-order under `'strict'` and throws. The throw propagates **back up** through the source's `'event'` listener fan-out into `live.push()`. Per a drift-harness snapshot taken **before** wiring `partitionOrdering` through to `partitionBy`:

```
late.eventsLateAtIngestTotal     195
late.pondInsertThrowsTotal       194    ← 99.5% of late events crash partitioning
pond.stats().rejected              0
```

The error message — `"out-of-order event: timestamp X is before latest Y"` — is the **strict-mode** error, despite the source being `'reorder'`. Confusing because the user's mental model says "I configured this `LiveSeries` for reorder, why is it strict-erroring."

Pond's docs ([`LivePartitionedSeries.d.ts`](node_modules/pond-ts/dist/LivePartitionedSeries.d.ts) line 36) do say `ordering` defaults to `'strict'`, and the `collect()` doc explicitly notes:

> Per-partition `LiveSeries` instances default to `'strict'` ordering. If the source uses `ordering: 'reorder'`, ... pass `{ ordering: 'reorder', graceWindow: ... }` to `collect`

But the equivalent caveat for `partitionBy` itself is buried (the line above only shows up in `apply` / `collect`). For the late-data brief specifically, this is the single line that decides whether the experiment runs at all — it should be the first line of the brief's Phase 2 instructions, or pond should default partition ordering to inherit from the source.

**Suggested library change.** Either:
- A. Default `LivePartitionedOptions.ordering` to inherit the source's `ordering` (and `graceWindow` / `retention` likewise — currently the docs say "the source `LiveSource`'s own retention does not propagate", which is the same trap shape).
- B. Throw `ValidationError` at construction when `source.ordering === 'reorder'` and `partitionBy(...)` doesn't pass an explicit `ordering`. Loud failure beats silent strict-on-reorder.

Either resolves the footgun. (A) is the more ergonomic choice but breaks the "explicit config every layer" pattern; (B) is the cheaper / safer one.

The experiment now passes `partitionOrdering` + `partitionGraceWindowMs` through `AggregateOptions` → `partitionBy('host', { ordering, graceWindow })` — the [`packages/aggregator/src/index.ts`](../packages/aggregator/src/index.ts) wiring shows the shape that works end-to-end.

## Workload characterisation — what the producer emits

Late-event injection is parameterised by `(fraction, delayMean, delayTail, hostBias, seed)`. Default knobs that the drift harness uses:

| knob | default | meaning |
| --- | --- | --- |
| `LATE_EVENT_FRACTION` | `0.05` | base per-event probability of being held |
| `LATE_EVENT_DELAY_MS` | `5000` | log-normal **median** delay |
| `LATE_EVENT_DELAY_TAIL_MS` | `15000` | log-normal **p99** delay |
| `LATE_EVENT_HOST_BIAS` | (unset) | per-host extra fraction, e.g. `api-3:0.5` |
| `LATE_EVENT_SEED` | `1` | RNG seed (mulberry32) — reproducibility |

Reproducibility is hard-pinned: the [`packages/producer/src/lateInjector.test.ts`](../packages/producer/src/lateInjector.test.ts) suite asserts that two runs with the same seed produce identical on-time / late partitions for the same input batch. Two runs with different seeds produce demonstrably different partitions (catches a future RNG regression). The simulator (CPU walk noise, anomaly bursts, `requests` count, per-event noise) is also seeded via `SIMULATOR_SEED` env / `simulatorSeed` option so the drift harness's A/B legs share the same underlying workload — Codex review of round 1 caught that the simulator was still using `Math.random()` and inflating the noise floor. Lateness reservoir tracks p50/p99 of the actual delays drawn — at the configured `(median=2s, p99=10s)` the harness measures producer-side `p50/p99 = 1846/8452 ms` and aggregator-side `lag p50/p99 = 1718/8370 ms`, well within the parameter bounds.

On the wire, `events_emitted_total` and `events_emitted_late_total` come from the producer's `/metrics` endpoint (only listens when `LATE_EVENT_FRACTION > 0`). The aggregator-side counters in `MetricsSnapshot.late.*` mirror these for the conservation check (next section).

## Conservation check — pond.stats() + experiment counters together

Each event from the producer either:
- arrives at pond's `#insert` and succeeds (counted in `live.stats().ingested`),
- arrives at `#insert` and throws under `'strict'` / `'reorder'`-past-grace (counted in the experiment's `late.pondInsertThrowsTotal` via the per-row push fallback in [`ingest.ts`](../packages/aggregator/src/ingest.ts)),
- or arrives and is silently rejected under `'drop'` (`live.stats().rejected`).

So:

```
producer.events_emitted_total
  ≈ pond.stats().ingested + late.pondInsertThrowsTotal + pond.stats().rejected
```

Drift harness output for the canonical 60s × 3-replicate workload (`api-1:0.5` bias, base-fraction `0.1`, 4 hosts × 10 events/s, simulator + late-injector both seeded):

```
producer events_emitted_total           7,698   (across 3 late-loaded replicates)
pond.stats().ingested                   7,662
late.pondInsertThrowsTotal                  0   (after partitionBy fix)
pond.stats().rejected                       0
                                        ─────
                                        7,662
                                        0.47% drift
```

**Drain on shutdown.** The first version of the harness saw a ~1% drift purely from events still pending in the producer's setTimeout queue when the harness sent SIGTERM. The producer's shutdown handler now calls `lateInjector.drain()` (force-fires every held timer synchronously), sleeps 200ms to let the gRPC writer flush the drained events, then runs the gRPC server's `stop()` (which is itself patched to fall back from `tryShutdown` → `forceShutdown` after 500ms — without that fallback, an active subscribe stream from the aggregator would deadlock the shutdown indefinitely).

The conservation check is the right shape: as long as `live.stats()` exposes `ingested` / `rejected` and the experiment exposes its own throw count, the wire is self-describing. **No library change needed here.** The library agent's instinct to expose `stats()` rather than make the experiment scrape internal counters was the right call.

## The milestone-B-relevant counters

For the canonical 60s × 3-replicate run (numbers from replicate 3, drift harness output):

```
late.eventsLateAtIngestTotal                  562   (matches producer.events_emitted_late_total)
  of which: within-rolling-window (1m)        562   ← all of them; the milestone-B-payoff scenario
  of which: past-rolling-window (>60s)          0
  of which: past-grace (>30s)                   0
late.lag p50/p99 ms                       1719/8373
```

**Every event in the within-rolling-window class is one pond's rolling does not retroactively repair.** The events are inserted into the source `LiveSeries` correctly under `'reorder'`, propagate through the per-partition sub-series (under the `partitionOrdering: 'reorder'` workaround), and are visible to the rolling at their insertion-point tick onward — but the rolling's previously-emitted ticks for the windows they fall into are not retroactively shifted. That's the gap milestone B is meant to close.

The per-host distribution under `LATE_EVENT_HOST_BIAS=api-1:0.5`:

```
late-events within rolling window, by host (replicate 3):
  api-1   379   ← biased: base 0.1 + bias 0.4 = effective 0.5; 67% of all late events
  api-2    68
  api-3    61
  api-4    54
```

The bias works as designed and is pinned by a 1000-event statistical unit test (`api-1:0.5` produces 5× the late count of unbiased hosts within ±25% tolerance). The friction note's payoff is that this *should* produce measurable per-host drift in `cpu_avg`, and it does (next section).

## Drift signal — does the rolling-repair gap matter?

A single A/B run can't separate "drift caused by pond's rolling-no-repair gap" from "drift caused by tick-scheduling jitter between two runs of the same workload." The library-agent's M4 review flagged this confound on the original single-replicate version. The drift harness now runs **N replicates per leg** with a different seed each time and reports `drift / σ_baseline` — drifts above ~2σ are confidently real, below ~1σ are within the run-to-run noise floor of the clean-baseline leg itself.

**Both the simulator AND the late-injector use seeded RNG.** The first cut of the multi-replicate harness only seeded the late-injector — the simulator's CPU walk noise / anomaly bursts / requests counts all came from `Math.random()`, so the A/B legs of one replicate didn't share an underlying workload (only the late-injection layer did). Codex review of the round-1 response caught this: baseline variance was absorbing uncontrolled simulator randomness alongside the legitimate tick-scheduling jitter, inflating the noise floor. The current harness threads `simulatorSeed = lateEventSeed` so within a replicate both legs see the **same simulated workload** — only the late-injection layer differs. Across replicates, the seed varies, which is the legitimate source of independence.

Run: `--hosts=4 --eps=10 --seconds=60 --replicates=3 --late-fraction=0.1 --late-delay-ms=2000 --late-delay-tail-ms=10000 --host-bias=api-1:0.5 --seed=1` (replicate seeds: 1, 2, 3; `simulatorSeed = lateEventSeed` so within each replicate both A/B legs share the same underlying workload).

```
per-host cpu_avg drift (mean ± stdev across 3 replicates):
  host    baseline             late                 drift     drift/σ_baseline
  ──────────────────────────────────────────────────────────────────────────────
  api-3   0.6535  ±0.0165      0.6548  ±0.0172      +0.0012      +0.07σ   (within noise)
  api-1   0.5580  ±0.0107      0.5585  ±0.0103      +0.0006      +0.05σ   (within noise)
  api-2   0.4716  ±0.0087      0.4718  ±0.0093      +0.0002      +0.02σ   (within noise)
  api-4   0.5137  ±0.0140      0.5137  ±0.0142      -0.0000      -0.00σ   (within noise)

noise floor (max baseline-leg stdev across hosts): 0.0165 (cpu_avg units)
```

**With both random sources properly seeded, the drift signal collapses to within noise on every host, including the heavily-biased one.** The earlier `-2.98σ` "real signal" finding was an artefact of uncontrolled `Math.random()` variance in the simulator's CPU walk and per-event noise — not the rolling-no-repair gap. Round 1 of the harness only seeded the late-injector; round 2 (per the Codex review's catch) seeds both. Once that confound is removed, the empirical drift at this measurement methodology is `≤0.07σ` across every host.

**This does not disprove the rolling-no-repair gap.** Pond's rolling-no-repair behaviour is documented and verified by inspection of `LiveRollingAggregation.ts`. What this measurement DOES show is that the gap doesn't manifest as **last-tick `cpu_avg` drift** at the experiment's measurement window. There's a structural reason: at the last measurement tick, the rolling's 60s window covers `[last_tick − 60s, last_tick]`, and **every late event delivered within the 30s grace window has had time to arrive in pond's buffer by then** (run is 60s + 5s warmup; producer's late tail at p99=10s lands well within). Pond's rolling, when it computes `cpu_avg` at the last tick, sees the same set of events in both legs — the late events ARE in pond's buffer in the late-loaded leg, just inserted at their reorder position — and produces the same average.

The gap WOULD be observable at:
- **Intermediate-tick measurements** before the late events arrive (early ticks in the late-loaded leg are missing the late events; pond's rolling's running state never gets retroactively shifted when those events later arrive).
- **Higher-moment metrics** like `cpu_sd` over short rolling windows (variance is more sensitive to within-window event ordering than the mean).
- **Workloads where late events leak past the rolling's window** (`LATE_EVENT_DELAY_TAIL_MS > rolling-window`), so the late event's `timeMs` is already evicted from pond's logical span by the time it arrives — the rolling SKIPS it entirely. This is the "past-rolling-window" classifier at this experiment, currently always 0.

The friction-note recommendation below adjusts: milestone B is **less urgent than the round-1 numbers suggested at this measurement methodology**, but the gap is real per pond's own docs and the experiment hasn't ruled out scenarios that would surface it.

## Pond gaps catalogue (per-pipeline-stage status)

The brief asked which pond pipeline stages currently handle late events correctly vs. which silently drop / miscount. From the docs + the experiment's measurements:

| stage | grace-correct? | rolling-repair? | notes |
| --- | --- | --- | --- |
| `LiveSeries` source (`'reorder'` + `graceWindow`) | ✅ | n/a | works as documented |
| `LivePartitionedSeries` sub-series | ✅ *if* `partitionBy({ ordering, graceWindow })` is set | n/a | the footgun above |
| `LiveAggregation` (`Sequence.every(...)` triggered) | ✅ within grace | ❌ closed buckets stay closed | per pond docs |
| `LiveRollingAggregation` / `LiveFusedRolling` | ✅ within grace | ❌ no rolling repair | the milestone-B gap |
| `LiveReduce` | ✅ within grace | ❌ same as rolling | per pond docs |

The "✅ within grace" column is what the source's `'reorder'` mode delivers: the late event is positioned correctly in the buffer, listeners fire, and downstream pipelines see it as a fresh event at its insertion point. The "❌ no rolling repair" column is the gap milestone B is meant to close.

## Recommendation: milestone-B sequencing

**The experiment recommends milestone B is *worth doing* but should be sequenced behind the partitionBy ordering footgun.** Two recommendations:

1. **First (cheap, days)** — fix the partitionBy ordering footgun via either default-inherit (option A) or explicit-throw (option B). Without this, every user who sets `ordering: 'reorder'` on a partitioned source hits the same crash the experiment did. A single line in the d.ts docstring isn't enough; the fix has to be at the API.

2. **Then (capability, weeks) — but lower-priority than the round-1 read suggested.** Implementing the rolling-repair semantic for `LiveRollingAggregation` / `LiveFusedRolling` / `LiveReduce` is documented as a real gap in pond, and at adversarial measurement styles (intermediate-tick reads, short-window cpu_sd, past-grace events) it would matter. But at the experiment's natural measurement methodology — last-tick `cpu_avg` over a 60s rolling window, with late events whose delay tail lands inside the rolling window before the measurement closes — the drift is `≤0.07σ` across every host. The gap is real but its **dashboard-visible payoff at moderate workloads is ~zero**.

   This bumps milestone B down the priority stack vs. the round-1 read. If the library agent has roadmap items competing for the same time slot — particularly the partitionBy ordering footgun fix from #1 above, or other capability work the experiment hasn't surfaced — those should run first. The case for milestone B reopens for the workloads it would actually surface in:
   - Real-time dashboards reading INTERMEDIATE rolling emits (not just the final settled state).
   - Streaming alerting that gates on rolling `cpu_sd` rather than `cpu_avg` (variance is more sensitive to event ordering).
   - Workloads where the producer's late tail leaks past the rolling's window (`delay_tail > rolling_window`).

   The experiment's current measurement style doesn't hit any of those; a follow-up that does would re-test the case for milestone B with a sharper signal.

(The earlier draft of this note proposed a third recommendation — surface `eventsLateWithinRollingWindowTotal` as a built-in pond counter so users can detect rolling-no-repair drift without per-experiment instrumentation. The library-agent review correctly flagged this as premature: the counter only earns its spot in the pond surface area if milestone B ships. Without milestone B the counter says "you're losing data" with no library-side recourse — that's an experiment-side tool, not a library API. Park the discussion under milestone B's design pass: a library that DOES repair late events would naturally expose "events repaired" / "events past grace" counters as part of the repair contract, and the right shape is best decided at design time alongside the repair semantic itself.)

**The milestone-B-relevant question, answered (with a surprise):** at realistic experiment loads (4 hosts × 10 events/s × 10% late + 50% biased on one host) and the experiment's natural measurement style (last-tick `cpu_avg` over a 60s rolling window), drift between repair-correct and current behaviour is **within the run-to-run noise floor on every host** (`≤0.07σ`). Round 1 of the analysis showed `-2.98σ` real-looking signal, but that turned out to be uncontrolled `Math.random()` variance in the simulator (Codex review caught the gap; round 2 added `simulatorSeed` plumbing, which collapsed the signal). **Milestone B is real per pond's docs, but its user-visible payoff at this measurement style is essentially zero**, so its priority should be lower than the round-1 read suggested. The experiment hasn't ruled out measurement styles where the gap would manifest — intermediate-tick reads, short-window variance, past-window late events — but those weren't part of this milestone's scope.

The headline value of the M4 work is therefore the **partitionBy ordering footgun finding** (recommendation #1 above), not the rolling-repair drift signal. The footgun would crash any user trying to use `'reorder'` mode on a partitioned source, regardless of measurement style; that's a higher-impact fix than the rolling-repair semantic at the workloads this experiment characterises.

## Reproducibility

Drift comparison harness (multi-replicate):

```bash
nvm use 22
pnpm --filter @pond-experiment/aggregator drift:late-data \
  --hosts=4 --eps=10 --seconds=60 --replicates=3 \
  --late-fraction=0.1 --late-delay-ms=2000 --late-delay-tail-ms=10000 \
  --host-bias=api-1:0.5 --seed=1
```

(`--replicates=1` skips the noise-floor stats and runs ~1/3 the wall-clock; useful for iteration. The 3-replicate version is the canonical run for friction-note updates.)

Aggregator standalone (e.g. for a longer dashboard run):

```bash
ORDERING=reorder GRACE_WINDOW_MS=30000 \
  pnpm --filter @pond-experiment/aggregator dev
LATE_EVENT_FRACTION=0.05 LATE_EVENT_DELAY_TAIL_MS=15000 \
LATE_EVENT_HOST_BIAS=api-3:0.05 \
  pnpm --filter @pond-experiment/producer dev
curl http://localhost:8080/metrics | jq '.late'
```
